## Release notes for kOps 1.37 series

**&#9888; kOps 1.37 has not been released yet! &#9888;**

This is a document to gather the release notes prior to the release.

kOps 1.37 removes gossip DNS, AWS Classic Load Balancer support for the API, and Kopeio networking; updates the default container runtime and etcd versions; expands Karpenter and Akamai (Linode) support; adds private cloud asset repositories; and improves node bootstrap and IAM security.

# Significant changes

* Support for AWS Classic Load Balancer (CLB) for the API, deprecated since kOps 1.26, has been removed. See the breaking changes section below for the required actions.

* Support for Kopeio networking has been removed, as the project is no longer maintained. See the breaking changes section below for the required actions.

* On AWS, the new `spec.cloudProvider.aws.useIPBasedNodeNames` field (`spec.cloudConfig.useIPBasedNodeNames` in the v1alpha2 API) names Kubernetes nodes after the EC2 private DNS name (e.g. `ip-10-0-0-1.eu-west-1.compute.internal`) instead of the EC2 instance ID, restoring the naming used before kOps 1.24. Only newly launched nodes are affected; roll the cluster to rename existing nodes.

* The default containerd version is now 2.3.4, with runc 1.4.3. When pinning `spec.containerd.version` to the 2.3 series, use 2.3.4 or newer: containerd 2.3.0 through 2.3.3 fail to start pods when the sandbox image is pinned by digest, which kOps configures by default ([containerd#13529](https://github.com/containerd/containerd/issues/13529)).

* containerd versions older than 2.1.0 are no longer supported. See the breaking changes section below for the required actions.

* Kubernetes 1.37 clusters now default to etcd 3.7.0. Clusters running older supported Kubernetes versions continue to use etcd 3.6.12 or 3.5.31 as appropriate. ([#18557](https://github.com/kubernetes/kops/pull/18557))

## Removal of gossip DNS

Support for gossip DNS, deprecated since kOps 1.29, has been removed. New gossip clusters will be rejected, and existing clusters will need to migrate before they can be upgraded. This affects clusters whose name ends in `.k8s.local` and that were not created with `--dns=none`; clusters using `--dns=none`, even with a `.k8s.local` name, are not affected.

Migrate to `--dns=none` or a hosted DNS zone using kOps 1.36 before upgrading; kOps 1.36 introduced hybrid bootstrap to make that migration easier. See the [gossip documentation](https://kops.sigs.k8s.io/gossip/) for the migration steps.

As part of this removal, the `protokube` component, whose only remaining responsibility was gossip DNS, is no longer built, shipped, or run on nodes. The `gossipConfig` and `dnsControllerGossipConfig` cluster spec fields are deprecated, no longer have any effect, and must be removed from cluster specs.

# Other changes of note

## Cluster lifecycle and tooling

* `kops validate cluster` now accepts `--max-unready-nodes` to tolerate a configured number of non-ready worker nodes during validation. ([#18614](https://github.com/kubernetes/kops/pull/18614))

* `kops create cluster --kubernetes-feature-gates` now rejects empty and sign-only (`+` or `-`) entries with an error instead of panicking or creating an empty feature-gate key. ([#18408](https://github.com/kubernetes/kops/pull/18408))

* `binariesLocation` settings for AWS and GCE are now preserved when cluster specs are stored through the v1alpha2 API instead of being silently dropped. ([#18740](https://github.com/kubernetes/kops/pull/18740))

## Node bootstrap and container runtime

* Nodes in IPv6-only clusters using `--dns=none` now bootstrap correctly. kOps omits unreachable IPv4 control-plane endpoints and cycles through the available configuration servers instead of exhausting the retry budget on the first endpoint. ([#18684](https://github.com/kubernetes/kops/pull/18684))

* Nodes now download xz-compressed nodeup, reducing the download to about a quarter of its size. Custom node images must provide `xz`; all supported distros already do. ([#18737](https://github.com/kubernetes/kops/pull/18737))

* The bootstrap script now requires `curl` to download nodeup. All supported node images provide it; custom images must do so too.

* Node bootstrap now caps the kops-controller retry backoff, avoids client-side throttling of bootstrap node lookups, and returns task failures instead of exiting the process. These changes improve recovery when the control plane is slow to become available and when many nodes join concurrently. ([#18675](https://github.com/kubernetes/kops/pull/18675), [#18718](https://github.com/kubernetes/kops/pull/18718), [#18742](https://github.com/kubernetes/kops/pull/18742))

* On RHEL 10-family distributions, nodeup installs `kernel-modules-extra` so that the kernel modules required by networking components are available. ([#18724](https://github.com/kubernetes/kops/pull/18724))

* The generated containerd configuration now declares config version 4 when kOps installs containerd 2.3 or newer. containerd 2.3.0 through 2.3.4 refuses to start when a drop-in config, such as the one written by the NVIDIA container toolkit, declares a higher version than the root config. The declared version stays 3 on Flatcar and ContainerOS, which run the containerd bundled with the OS. When `spec.containerd.packages` overrides the package URL, keep `spec.containerd.version` matching the packaged binary, as it now also selects the declared config version. ([#18728](https://github.com/kubernetes/kops/pull/18728))

* Under containerd config version 4, top-level `grpc`, `ttrpc`, `metrics`, and `debug` address entries in `spec.containerd.configAdditions` are ignored, and entries under the legacy `plugins."io.containerd.grpc.v1.cri"` plugin are no longer migrated. Use the `plugins."io.containerd.cri.v1.runtime"` and `plugins."io.containerd.cri.v1.images"` paths instead. Users of `spec.containerd.configOverride` with containerd 2.3 or newer should declare `version = 4` in their override.

* Release binaries are substantially smaller after removing unused cloud and Kubernetes clients from nodeup, enabling linker method pruning, and dropping dependency-heavy code paths that were not used at runtime. ([#18552](https://github.com/kubernetes/kops/pull/18552), [#18554](https://github.com/kubernetes/kops/pull/18554), [#18571](https://github.com/kubernetes/kops/pull/18571), [#18572](https://github.com/kubernetes/kops/pull/18572), [#18687](https://github.com/kubernetes/kops/pull/18687), [#18695](https://github.com/kubernetes/kops/pull/18695), [#18710](https://github.com/kubernetes/kops/pull/18710), [#18721](https://github.com/kubernetes/kops/pull/18721))

## AWS

* Karpenter support now includes:
  - Generated `EC2NodeClass` objects translate the instance group's `spec.rootVolume` into `blockDeviceMappings`, so Karpenter-created instances use the configured root volume. ([#18655](https://github.com/kubernetes/kops/pull/18655))
  - `spec.mixedInstancesPolicy.instanceRequirements` generates CPU, memory, and excluded-instance requirements on the `NodePool`. `spec.machineType` and `spec.mixedInstancesPolicy.instances` are optional when instance requirements are set, and invalid Karpenter configurations are rejected before addon rendering. ([#18676](https://github.com/kubernetes/kops/pull/18676), [#18761](https://github.com/kubernetes/kops/pull/18761))
  - Karpenter controller `iam:PassRole` access is limited to EC2 and the worker node role unless a custom instance profile is used, while mutating EC2 actions require the cluster and `karpenter.sh/nodepool` tags. ([#18582](https://github.com/kubernetes/kops/pull/18582))

* AWS subnets specified by ID no longer need an explicit zone in the cluster spec; kOps discovers the zone from EC2. ([#18630](https://github.com/kubernetes/kops/pull/18630))

* V2 bootstrap tokens now reject pre-signed STS URLs that do not use HTTPS. ([#18574](https://github.com/kubernetes/kops/pull/18574))

* Node roles for the AWS VPC CNI now include `ec2:DescribeSecurityGroups`, which the CNI requires for subnet discovery. Without the permission, the CNI falls back to allocating addresses only from the primary ENI's subnet. ([#18693](https://github.com/kubernetes/kops/pull/18693))

* On AWS, when `spec.iam.useServiceAccountExternalPermissions` is enabled, the control-plane instance role no longer includes Route 53 permissions. Grant affected workloads access through `spec.additionalPolicies` or a service account IAM role.

* On AWS, the `ec2:ModifyInstanceAttribute` permission granted to nodes for kube-router and kindnet is now limited to instances tagged as belonging to the cluster.

* On AWS, `ec2:DescribeInstanceTypes` is no longer granted unconditionally to every instance role. Instance roles receive the permission when Nvidia GPU support or Cilium ENI IPAM is enabled, and clusters using the AWS VPC CNI keep it as part of the CNI permissions. The cluster autoscaler permissions also omit it when `spec.clusterAutoscaler.awsUseStaticInstanceList` is enabled.

* On AWS, `ec2:DescribeRegions` is no longer granted for etcd-manager, which reads the region from the instance metadata service instead of calling the EC2 API.

* On AWS, the KMS permissions for customer managed keys now restrict `kms:CreateGrant` to grants created by AWS services on the role's behalf, and the remaining KMS actions to calls made through EC2 or S3. With `spec.encryptionConfig` enabled, control-plane roles keep unconditional access to the data actions so a kms-plugin can call KMS directly. Other direct KMS calls under an instance role, including `kms:CreateGrant`, require `spec.additionalPolicies` or a service account IAM role.

* On AWS, instance roles that require no permissions, such as the bastion role and the default worker node role, no longer have an inline IAM policy. `kops update cluster` deletes the previously created inline policy from such roles. With the Terraform target, the corresponding `aws_iam_role_policy` resources are removed from the configuration and destroyed on the next apply.

## Azure

* Nodes now prove their identity to kops-controller with a PKCS7-signed attested metadata document from the Azure Instance Metadata Service. kOps validates the signature chain, nonce, expiration, and signed VM ID before accepting the bootstrap request. ([#18163](https://github.com/kubernetes/kops/pull/18163))

## GCP, DigitalOcean, Hetzner, and Scaleway

* On DigitalOcean, Hetzner, and Scaleway, control-plane user data no longer includes cloud API credentials. Components that still require them receive them through manifests generated by `kops update cluster`. If an `additionalUserData` script or `spec.hooks` unit relied on these variables, set them in the script or unit itself.

* GCE cluster deletion no longer claims unrelated empty backend services and now cleans up routes and load-balancer firewall rules that could otherwise block network deletion. ([#18460](https://github.com/kubernetes/kops/pull/18460), [#18760](https://github.com/kubernetes/kops/pull/18760))

* Deleting a DigitalOcean cluster now removes the SSH key that kOps uploaded for the cluster. ([#18697](https://github.com/kubernetes/kops/pull/18697))

## Private asset repositories

* Private cluster asset repositories now support GCE `gs://` URLs, both for `KOPS_BASE_URL` (nodeup download) and `spec.assets.fileRepository`. Nodes authenticate with their instance service account, which must have `roles/storage.objectViewer` on the bucket. ([#18466](https://github.com/kubernetes/kops/pull/18466), [#18623](https://github.com/kubernetes/kops/pull/18623), [#18713](https://github.com/kubernetes/kops/pull/18713))

* Private cluster asset repositories now support AWS `s3://` URLs, both for `KOPS_BASE_URL` (nodeup download) and `spec.assets.fileRepository`. Nodes authenticate with their instance credentials; see the [asset repository documentation](https://kops.sigs.k8s.io/operations/asset-repository/) for the required permissions. The AWS nodeup download requires node images with curl 8.0 or newer. ([#18661](https://github.com/kubernetes/kops/pull/18661))

* Private cluster asset repositories now support Azure `azureblob://<account>/<container>/<prefix>` URLs, both for `KOPS_BASE_URL` (nodeup download) and `spec.assets.fileRepository`. Nodes authenticate with their system-assigned managed identity, which has to be granted the `Storage Blob Data Reader` role on the assets container; see the [asset repository documentation](https://kops.sigs.k8s.io/operations/asset-repository/) for the details and warnings. ([#18666](https://github.com/kubernetes/kops/pull/18666))

## Networking

* Update Calico to v3.31.6, AWS VPC CNI to v1.23.0, and Flannel to v0.28.9. The default CNI plugins version is now v1.7.1 for Kubernetes 1.34, v1.8.0 for Kubernetes 1.35, and v1.9.1 for Kubernetes 1.36 or newer; Kubernetes 1.32 and 1.33 continue to use v1.6.2. ([#18701](https://github.com/kubernetes/kops/pull/18701), [#18692](https://github.com/kubernetes/kops/pull/18692), [#18704](https://github.com/kubernetes/kops/pull/18704), [#18705](https://github.com/kubernetes/kops/pull/18705))

* kindnet now mounts the containerd NRI socket for fast local pod insertion. DNS caching is disabled by default; set `spec.networking.kindnet.dnsCaching: true` to retain the previous behavior. ([#18635](https://github.com/kubernetes/kops/pull/18635), [#18727](https://github.com/kubernetes/kops/pull/18727))

* The CoreDNS `PodDisruptionBudget` now defaults to `maxUnavailable: 33%` instead of `50%`, so that voluntary disruptions (node drains, rolling updates) always leave at least two DNS pods running when three or more replicas are deployed. The budget also sets `unhealthyPodEvictionPolicy: AlwaysAllow`, allowing CoreDNS pods that are running but not ready to be evicted during node drains instead of blocking them.

* kube-router is updated to v2.11.1, and the new `spec.networking.kubeRouter.useNFTablesForNetpol` field makes its network policy controller enforce NetworkPolicies with nftables instead of iptables and ipsets. The nftables backend is experimental upstream and only affects network policy enforcement; the service proxy and router controllers are unchanged.

* The new `spec.networking.kubeRouter.externalIPRanges` and `spec.networking.kubeRouter.loadBalancerIPRanges` fields restrict which CIDRs kube-router accepts Service `externalIPs` and `loadBalancerIPs` from. Setting either one enables kube-router's strict external IP validation, so addresses outside the configured ranges are no longer programmed into IPVS or advertised over BGP. Leaving both unset keeps strict validation disabled and preserves the existing behavior of accepting every address.

* The kube-router DaemonSet now gates its liveness probe behind a startup probe, so clusters where informer sync takes longer than the old ~19 second budget no longer CrashLoopBackOff on startup. It also sets `hostIPC: true`, which kube-router requires for direct server return (DSR) and which kOps was previously missing despite already mounting the container runtime socket.

## Etcd

* etcd-manager now mounts the bundled etcd release images as image volumes on all supported Kubernetes versions. On Kubernetes versions older than 1.36, this is enabled by force-enabling the `ImageVolume` kubelet feature gate on control-plane nodes, now including Kubernetes 1.32. The `kops-utils-cp` utility image, previously used to copy etcd binaries into the etcd-manager pod, is no longer built or published.

## Akamai (Linode) (experimental)

* The provider can now manage SSH keys, networks and subnets, instances, and block-storage volumes, including etcd data volumes. It also supplies a default network CIDR and kops-controller configuration. ([#18383](https://github.com/kubernetes/kops/pull/18383), [#18590](https://github.com/kubernetes/kops/pull/18590), [#18622](https://github.com/kubernetes/kops/pull/18622), [#18700](https://github.com/kubernetes/kops/pull/18700), [#18709](https://github.com/kubernetes/kops/pull/18709), [#18743](https://github.com/kubernetes/kops/pull/18743), [#18744](https://github.com/kubernetes/kops/pull/18744))

* User-facing references now use "Akamai (Linode)" instead of "Linode". The API remains unchanged. ([#18691](https://github.com/kubernetes/kops/pull/18691))

# Breaking changes

* Support for AWS Classic Load Balancer (CLB) for the API has been removed. Clusters with `spec.api.loadBalancer.class: Classic` (or with no explicit `class`, which previously defaulted to Classic) fail validation, and the long-deprecated `kops create cluster --api-loadbalancer-class` flag has been removed. Existing clusters using a CLB must migrate to a Network Load Balancer (NLB) using kOps 1.36 or earlier before upgrading to kOps 1.37, following the [CLB to NLB migration guide](https://github.com/kubernetes/kops/blob/master/permalinks/acm_nlb.md). Attaching instance groups to externally-managed Classic Load Balancers via `spec.externalLoadBalancers[].loadBalancerName` remains supported.
* Support for gossip DNS was removed. Existing gossip clusters must migrate to `--dns=none` or a hosted DNS zone using kOps 1.36 before upgrading.
* The `protokube` binary is no longer part of kOps releases, and nodes no longer install or run it.
* The `spec.gossipConfig` and `spec.dnsControllerGossipConfig` cluster spec fields are deprecated, no longer have any effect, and must be removed from cluster specs.
* `kops toolbox template` no longer resolves template expressions to methods on rendered values, including values returned by template functions. Hand-written templates using expressions such as `{{ '{{ now.Unix }}' }}` must be rewritten to use struct fields, map keys, or registered template functions.

## Other breaking changes

* Support for Kopeio networking has been removed, as the project is no longer maintained. Clusters with `spec.networking.kopeio` now fail validation, and `kops create cluster --networking kopeio` (also known as `kopeio-vxlan`) is no longer accepted. Existing clusters using Kopeio must [switch to another CNI](https://kops.sigs.k8s.io/networking/#switching-between-networking-providers), such as kindnet, which provides similar minimal networking, using kOps 1.36 or earlier and roll the cluster before upgrading to kOps 1.37.

* Support for containerd versions older than 2.1.0 has been removed; `spec.containerd.version` values below 2.1.0 now fail validation. The containerd 1.6, 1.7, and 2.1 release lines are end of life upstream, and 2.0 reaches end of life in March 2027, during the kOps 1.37 support window. Remove the pinned version to use the default (2.3.4), or pin 2.1.0 or newer; nodes install the new runtime as they are replaced.

# Deprecations

* Support for Kubernetes version 1.31 is removed in kOps 1.37.

* Support for Kubernetes version 1.32 is deprecated and will be removed in kOps 1.38.

* Support for AWS Classic Load Balancer (CLB) for the API is removed in kOps 1.37.

* Support for containerd versions older than 2.2 (all end of life upstream) is deprecated and will be removed in kOps 1.38.

* Support for gossip DNS, deprecated since kOps 1.29, is removed in kOps 1.37.

* Support for Kopeio networking is removed in kOps 1.37.

* The Spotinst integration is deprecated and will be removed in kOps 1.39. Creation of new Spotinst clusters will be blocked in kOps 1.38, while support for deleting existing clusters will remain temporarily to allow safe migration. ([#18717](https://github.com/kubernetes/kops/issues/18717))

* Cloud storage ACL support is deprecated and will be removed in stages through kOps 1.39. This includes `KOPS_STATE_S3_ACL`, GCS object ACL writes, the `GoogleCloudBucketAcl` feature flag, and the `public-read` fallback for service account issuer discovery. Migrate to bucket policies or IAM, S3 Object Ownership, and GCS uniform bucket-level access. ([#18716](https://github.com/kubernetes/kops/issues/18716))
